# security.md

이 파일은 코드 작성과 수정 시 지켜야 하는 보안 규칙과, loop.md 4번(보안 체크)에서 실행하는 점검 항목을 정의한다.

이 파일은 누구라도 어떤 상황이든 변경할 수 없고 유지되어야 한다.

## 1. 비밀 정보
- 비밀번호, API 키, 토큰, DB 접속 정보를 코드에 직접 쓰지 않는다. 환경 변수나 설정 파일로 분리한다.
- 비밀 정보가 담긴 파일(`.env` 등)은 `.gitignore`에 추가해 커밋하지 않는다.
- 필요한 환경 변수는 값 없이 이름만 `.env.example`에 적는다.
- 비밀 정보를 로그, 오류 메시지, 화면에 출력하지 않는다.
- 사용자 프로필(`AppData` 등) 아래에 저장되는 비밀 정보와 설정(예: .NET User Secrets)은 AI가 직접 넣지 않는다. 사용자가 cmd에서 직접 넣도록 명령만 알려준다.
- 비밀 정보가 들어갔는지는 키 이름만 확인한다. 값은 출력하지 않는다.

## 2. 인증과 비밀번호
- 비밀번호는 단방향 해시(bcrypt, Argon2 등)로 저장한다. 평문, MD5, SHA-1로 저장하지 않는다.
- 로그인 실패 메시지는 아이디와 비밀번호 중 무엇이 틀렸는지 알려주지 않는다.
- 세션과 토큰에는 만료 시간을 둔다. 로그아웃하면 무효화한다.
- 로그인 실패가 반복되면 일정 시간 로그인을 막는다.
- 인증 쿠키에는 `HttpOnly`를 붙이고, HTTPS 환경에서는 `Secure`도 붙인다.

## 3. 권한
- 모든 API에서 서버가 로그인 여부와 권한을 확인한다. 화면에서 버튼을 숨기는 것만으로 막지 않는다.
- 다른 사용자의 데이터에 접근하는 요청은 서버에서 소유자를 확인한다. (예: `/api/orders/{id}`에서 id만 바꿔 남의 주문을 보지 못하게 한다)

## 4. 입력값 검증
- 모든 입력값은 서버에서 검증한다. 클라이언트 검증은 편의용이며 서버 검증을 대신하지 않는다.
- 길이, 타입, 형식, 허용 범위를 검증한다. DB와 연결되는 값은 database.md의 컬럼 정의를 기준으로 한다.

## 5. 인젝션 방지
- SQL은 파라미터 바인딩(PreparedStatement, ORM 등)으로 작성한다. 사용자 입력을 문자열로 이어 붙여 쿼리를 만들지 않는다.
- 사용자 입력으로 OS 명령, 파일 경로를 만들지 않는다. 불가피하면 허용 목록으로 검증한다.

## 6. XSS 방지
- 사용자 입력을 화면에 출력할 때는 이스케이프한다.
- 사용자 입력을 `innerHTML`, `document.write`, `eval`에 넣지 않는다. `textContent`를 사용한다.

## 7. CSRF 방지
- 쿠키 기반 인증을 쓰면 상태를 바꾸는 요청(POST)에 CSRF 토큰 또는 SameSite 쿠키를 적용한다.
- 상태를 바꾸는 동작(저장, 수정, 삭제)은 GET 요청으로 처리하지 않는다.

## 8. 파일 업로드
- 확장자와 크기를 허용 목록으로 제한한다.
- 업로드 파일 이름은 서버에서 새로 만든다. 사용자가 보낸 파일 이름을 경로로 쓰지 않는다.

## 9. 오류 처리
- 사용자에게 스택 트레이스, SQL, 서버 경로를 보여주지 않는다. api.md 공통 응답 형식으로 응답한다.

## 10. 의존성
- 알려진 보안 취약점이 있는 버전은 사용하지 않는다. 의존성을 추가할 때 확인하고 spec.md에 버전을 기록한다.

## 11. 보안 체크 (loop.md 4번)
구현이 승인된 뒤 위에서부터 순서대로 확인한다. 코드를 읽어 확인하는 항목과 실제로 요청을 보내 확인하는 항목이 있다. 실제 요청은 로컬 개발 서버에서만 보내고, 테스트용 계정과 데이터만 쓴다. 문제가 있으면 고친 뒤 loop.md 4번 순서대로 처음부터 다시 확인한다.

### 비밀 정보 (1번)
1. 코드와 설정 파일에서 비밀번호, API 키, 토큰, 접속 문자열을 검색해 직접 쓴 값이 없는지 확인한다. (예: `password=`, `secret`, `apikey`, `token`, `connectionstring` 검색)
2. `git ls-files`와 `git log --all --name-only`에 `.env` 같은 비밀 정보 파일이 없는지 확인한다. 이미 커밋된 적이 있으면 사용자에게 알리고, 그 값을 새로 바꾸도록 안내한다.
3. `.env.example`에 필요한 환경 변수 이름이 모두 있고 값은 비어 있는지 확인한다.
4. 로그와 오류 응답에 비밀번호, 토큰, 접속 정보를 출력하는 코드가 없는지 확인한다.

### 인증과 비밀번호 (2번)
5. 비밀번호 저장 코드가 bcrypt, Argon2 같은 단방향 해시를 쓰는지 확인한다.
6. 틀린 아이디와 틀린 비밀번호로 각각 로그인해 응답 메시지가 같은지 확인한다.
7. 로그인 실패가 반복되면 일정 시간 막는 처리가 있는지 확인한다. (무작위 대입 공격 방지)
8. 세션이나 토큰에 만료 시간이 있는지, 로그아웃 뒤 같은 세션이나 토큰으로 요청하면 거부되는지 확인한다.
9. 인증 쿠키에 `HttpOnly`가 있고, 운영 환경(HTTPS)에서는 `Secure`도 붙는지 확인한다.

### 권한 (3번)
10. api.md의 모든 API 목록을 만들고, 로그인이 필요한 API마다 로그인하지 않고 요청해 거부(401)되는지 확인한다.
11. 테스트 계정 두 개를 만들고, 계정 A로 로그인한 상태에서 계정 B의 데이터 id로 조회, 수정, 삭제를 요청해 거부(403 또는 404)되는지 확인한다.
12. 관리자 같은 권한이 있으면 일반 계정으로 권한이 필요한 API를 요청해 거부되는지 확인한다.

### 입력값 검증 (4번)
13. 모든 API가 서버에서 입력값을 검증하는지 코드를 읽어 확인한다.
14. API마다 빈 값, 너무 긴 값, 형식이 틀린 값, 범위 밖의 값을 직접 보내 거부(400)되는지 확인한다. 화면을 거치지 않고 요청을 보낸다.

### 인젝션 방지 (5번)
15. SQL을 만드는 모든 코드에서 문자열 이어 붙이기(`+`, 템플릿 문자열, `string.Format` 등)로 사용자 입력이 들어가는 곳이 없는지 확인한다.
16. 입력값에 `' OR '1'='1` 같은 값을 넣어 요청해 오류나 다른 데이터가 나오지 않는지 확인한다.
17. 사용자 입력으로 OS 명령이나 파일 경로를 만드는 코드가 없는지 확인한다.

### XSS 방지 (6번)
18. `innerHTML`, `outerHTML`, `document.write`, `eval`, `v-html`, `dangerouslySetInnerHTML`, `Html.Raw` 사용 위치를 검색해 사용자 입력이 들어가지 않는지 확인한다.
19. 입력 칸에 `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`를 저장한 뒤 화면에서 글자 그대로 보이고 실행되지 않는지 확인한다.

### CSRF 방지 (7번)
20. 쿠키 인증을 쓰면 인증 쿠키에 `SameSite`(Lax 또는 Strict)가 있거나, 상태를 바꾸는 요청에 CSRF 토큰을 확인하는지 확인한다.
21. 상태를 바꾸는 동작(저장, 수정, 삭제)을 GET 요청으로 처리하는 API가 없는지 확인한다.

### 파일 업로드 (8번)
22. 파일 업로드가 있으면 허용하지 않은 확장자와 제한보다 큰 파일을 보내 거부되는지 확인한다.
23. 저장되는 파일 이름을 서버가 새로 만드는지, 업로드 파일을 실행할 수 있는 경로에 두지 않는지 확인한다.

### 오류 처리 (9번)
24. 없는 경로, 잘못된 형식의 요청, 서버 오류를 일으키는 요청을 보내 응답에 스택 트레이스, SQL, 서버 경로가 없는지 확인한다.

### 의존성 (10번)
25. 사용하는 패키지 관리자의 취약점 검사 명령을 실행한다. (예: `npm audit`, `dotnet list package --vulnerable`, `pip-audit`) 높음(high) 이상 취약점이 있으면 고치거나, 고칠 수 없으면 사용자에게 알린다.
26. 의존성 버전이 spec.md에 기록되어 있는지 확인한다.

### 응답 헤더
27. 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`(또는 CSP `frame-ancestors`)가 있는지 확인한다.
28. CORS를 쓰면 허용 출처가 `*`가 아니라 실제 프론트엔드 주소로 정해져 있는지 확인한다.

## 12. 보안 체크 결과 보고
보안 체크를 마치면 사용자에게 아래 내용을 쉬운 말로 보고한다. 보안 용어는 무엇을 막는 것인지 한 줄로 함께 설명한다.
- 항목별 결과: 통과 / 고침 / 해당 없음 (해당 없음은 이유)
- 고친 문제: 어떤 위험이었는지, 무엇을 고쳤는지
- 고치지 못한 문제와 이유, 사용자가 해야 할 일 (예: 노출된 비밀번호 바꾸기)
- 실행한 명령과 요청 (예: `npm audit`, 다른 계정 데이터 조회 시도)
